# Chapter 19 research: map iterators and real-time ring-buffer telemetry

**Author: Providence Salumu**

The Linux kernel distinguishes two mechanisms called BPF iterators. A BPF iterator *program* is a `BPF_PROG_TYPE_TRACING` program invoked once per kernel object and exposed through `seq_file`; an open-coded iterator is a constructor/next/destructor kfunc trio whose termination contract is understood by the verifier. Chapter 19 uses the program form, specifically `iter/bpf_map_elem`, and explicitly distinguishes it from an ordinary userspace walk built from `BPF_MAP_GET_NEXT_KEY`. Source: [Linux BPF Iterators](https://docs.kernel.org/bpf/bpf_iterators.html), accessed 2026-09-10.

A map-element iterator must be attached to a specific map. The Linux UAPI carries that target in `union bpf_iter_link_info.map.map_fd` during `BPF_LINK_CREATE`; reading begins after `BPF_ITER_CREATE`. Aya 0.14 exposes `Iter::load(iter_type, btf)` and a parameterless `Iter::attach()`, but it does not expose the map-target link information through that high-level method. The sample therefore keeps loading in Aya and uses a narrowly scoped Rust wrapper for those two stable BPF syscall commands. Sources: Linux `include/uapi/linux/bpf.h`; [Aya 0.14 Iter](https://docs.rs/aya/0.14.0/aya/programs/iter/struct.Iter.html), accessed 2026-09-10.

Aya's per-CPU hash-map iterator uses `BPF_MAP_GET_NEXT_KEY` and then a per-CPU lookup for each key. Order is arbitrary. If a current key disappears, the kernel's next-key operation can restart at the first key, so concurrent deletion can cause repeats; kernel documentation recommends batch lookup when deletion is interleaved. The custom userspace iterator walks keys, reduces `PerCpuValues<TelemetryCounter>`, and skips a key that disappeared between the two syscalls. The result is best effort and does not make the whole walk point-in-time. Sources: [Linux hash map documentation](https://docs.kernel.org/bpf/map_hash.html); [Aya 0.14 HashMap](https://docs.rs/aya/0.14.0/aya/maps/hash_map/struct.HashMap.html), accessed 2026-09-10.

The BPF ring buffer is a map-backed multi-producer/single-consumer (MPSC) transport. A shared ring improves memory use and preserves reservation order across CPUs. Its capacity is a power of two. Reservation never blocks; it can fail because the buffer is full and can also fail in non-maskable interrupt context when reservation cannot acquire its internal spin lock. Reserve/submit avoids an extra data copy but requires a verifier-known constant record size. Every tracked reservation must be submitted or discarded on every reachable path. Sources: [Linux BPF ring buffer](https://docs.kernel.org/bpf/ringbuf.html); [Aya 0.14 RingBuf](https://docs.rs/aya/0.14.0/aya/maps/ring_buf/struct.RingBuf.html), accessed 2026-09-10.

Aya's userspace `RingBuf::next()` returns one borrowed record at a time and only one `RingBufItem` may be outstanding. When `next()` returns `None`, the consumer may wait on the map file descriptor through epoll, mio, or Tokio `AsyncFd`. Producer-side drop notification is not delivered as a synthetic record; the BPF program must count failed reserve/output operations separately. The sample retains its per-CPU `DROPPED` counter and reports userspace parse rejections independently.

The implemented live aggregate is a `BPF_MAP_TYPE_PERCPU_HASH`, so every tracepoint producer updates a CPU-local counter without a lock helper. The optional kernel iterator targets a separate `TELEMETRY_EXPORT` map populated after userspace reduction and left immutable for the iterator session. Verifier acceptance, helper availability, target BTF, and successful map-target attachment must be recorded for each supported kernel.

## Compatibility correction: tracepoints cannot use `bpf_spin_lock`

The first implementation draft used `bpf_spin_lock` in `telemetry_sys_enter`, which is a `BPF_PROG_TYPE_TRACEPOINT` program. That code compiles to BPF bytecode but would be rejected at load time because tracing programs, including tracepoints, cannot use the spin-lock helper due to insufficient preemption checks. The Linux helper documentation also requires BTF map-value metadata, one top-level lock, no helper or BPF-to-BPF calls while locked, and unlock on every path. Source: [bpf_spin_lock helper documentation](https://docs.ebpf.io/linux/helper-function/bpf_spin_lock/), accessed 2026-09-10.

The corrected design uses `BPF_MAP_TYPE_PERCPU_HASH` for the live hot path, which makes each CPU's updates race-free without a lock. The default custom Rust iterator reduces `PerCpuValues<TelemetryCounter>` into one snapshot per key. For the optional kernel `bpf_map_elem` iterator, user space first stages those merged values into a separate ordinary `TELEMETRY_EXPORT` hash map after the live observation window. The kernel iterator attaches to that quiescent export map and emits binary records. This keeps the tracepoint loadable and gives the iterator a coherent immutable source for the bounded read session.
